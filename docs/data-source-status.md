### 5.1 ⚠️ 重要更正：Day 18 的「网关剥前缀」结论有误（2026-10-06 实测）

Day 18 曾下过一个硬结论：**「函数内 `req.url` 永远是 `/`，原始路径不在任何请求头里，一个函数无法分辨自己被哪个路由调用」**。
本次核查发现**这个结论是错的**——错在测试用例选得不好。

**决定性证据**（2026-10-06 打真实网关）：

| 请求路径 | 网关 | 函数内 `req.url` |
| ---- | ---- | ---- |
| `/api/hot` | 命中路由 | `/`（前缀剥完正好空） |
| `/api/hot/` | 命中路由 | `/` |
| `/api/hot/a/b/c` | 命中路由 | **`/a/b/c`** ← 剩余部分保住了 |
| `/api/health/x` | 命中路由 | **`/x`** ← 同样保住 |
| `/api/favorites/20261006-n01` | 命中路由 | `/20261006-n01`（函数忽略了这个后缀，故仍返回列表） |
| `/api/favoritesX` | **不命中** | 网关直接 `INVALID_PATH` |

**修正后的正确理解**：

1. 网关路由是**前缀匹配**（`/api/hot` 能匹配 `/api/hot/a/b/c`，但 `/api/favoritesX` 不匹配 `/api/favorites`）。
2. 剥掉的是**路由自身那段前缀**，**剩余部分原样保留在 `req.url`**，函数完全能读到。
3. Day 18 之所以以为「恒为 `/`」，是因为当时只测了 `/api/hot` 和 `/api/favorites` 两个请求——它们的前缀剥完正好什么都不剩。

**「一个路由 = 一个云函数」这条仍然成立**（不同路径确实要拆函数），但**理由要改**：
不是「读不到路径」，而是**网关只把请求转发给前缀匹配上的那个函数**——`/api/news` 没有登记路由，请求根本进不了任何函数（网关层就 404 了）。

**对本次任务的实际影响**：

- ✅ `/api/news/:id`、`/api/leagues/:id` **可以按契约原样实现**（路径参数能透传）。
- ✅ 也可以让 `/api/news` 和 `/api/news/:id` **共用一个函数**，靠 `req.url` 区分（如 `req.url === '/'` → 列表，`/^\/([\w-]+)$/` → 详情）。
- ⚠️ 前端已有代码用的是 `/api/leagues/<lg>`（如 `/api/leagues/nba`），**现在这条路走得通了**，不用改前端。
- 📌 **要回写 `api-contract.md` 与 `cloudbase-deploy-day18.md`**：修订那条错误结论，并更新 `cloudfunctions/api/index.js` 里的注释（那里写着「恒为 `/`」）。

## 六、为什么 Day 18 要这么设计（降级不是失误）

前端每个 fetch 都写成：

```js
try { 调接口 } catch { 读本地 JSON }
```

好处：**接口没上线的日子，页面也不会白屏**——仍能展示示例数据，方便做样式和交互。代价就是现在这个现象：看起来像「只有一页有真数据」。

这是刻意为之的过渡态，等接口补齐，同一套代码自动切到真数据，**不用再改前端**。
