## 0. 一句话

> 今天要找的不是「功能哪里不好」，而是 **「他卡在哪里」**。  
> 卡点往往是产品内部完全没有概念的地方（一句没说清的文案、一个顺序不对的按钮、一个他不知道要去哪找的编号）——  
> 所以这份脚本**刻意不解释原理**，只写「点什么」，还故意留了 2 处含糊话。  
> 他犹豫的那一下，就是今天要的答案。

## 1. 试用链路（本项目版）

课程给的示例是打卡应用：打开 → 打卡 → 刷新确认 → 修改 → 删除。  
《每日体坛速览》是**读为主**的站，没有「打卡」，**对应的完整写操作闭环只有一条**，在接口检查台页：

| 课程里的动作      | 本项目对应的动作                       | 页面               |
| ----------- | ------------------------------ | ---------------- |
| 打开链接、看到核心数据 | 打开首页，看到三平台真实热搜（数据来自公网接口，不是写死的） | `index.html`     |
| 完成一次核心操作    | 在接口检查台「写入测试」里点一下，真写一行进数据库      | `checkup.html` ③ |
| 刷新确认        | 刷新页面，看那一行还在不在（数据在库里，不在浏览器里）    | `checkup.html` ② |
| 修改          | 按 id 取出这一行，改一个字段，提交            | `checkup.html` ④ |
| 删除          | 删掉它——这里会弹**二次确认**，取消/确定各来一次    | `checkup.html` ④ |

## 2. 邀请话术（复制给对方，别加解释）

### 2.1 默认用 A：把「风险提醒」那一关带过去

> 帮我个忙，5 分钟。  
> 我做了个看体育新闻的小网站，想请一个完全没参与过的人试着用一下，看看哪里让人摸不着头脑。  
> 链接是：`https://ross-d2gimwy406e0d6812-1499705719.tcloudbaseapp.com/index.html`  
> **打开之后如果中间跳出一个提示页，按页面上的提示继续就行**（那是腾讯云给的测试域名提示，不是出错了）。  
> 下面是 12 个小步骤，你照着点就行。**不要问我怎么做**，卡住了就照着你自己的想法试；实在过不去就跳过，把那一下记下来——那是帮我，不是耽误事。  
> 全程请你**边点边把看到的话念/抄给我**（我下面对应着做了张小表）。  
> 用你自己的手机或电脑都行，就用你平时上网的那个浏览器。

**为什么这么写**：这一关是测试域名自带的、今天修不了（见 §1.1），  
而今天的完成标准是「**一位真人独立走完核心流程**」——  
如果把试用卡在关不掉的门上，后面 10 步的卡点一个都收不到。所以用一句**中性、不给答案**的话带过去，  
同时在记录表里**如实记下他过这一关时有没有犹豫**（第 2 步就是这么用的）。

### 2.2 备选 B：想专门测这一关，就把上面加粗那句话删掉

保留原样、什么都不说。适合「今天已经有人能走完、想额外看看门槛有多高」的时候。  
**代价**：很可能他的记录就停在第 1 步了，后面收不到东西。选 B 就只当是「量一下门槛」用。

### 2.3 不要说的三句话（一说就等于把答案送出去了）

「检查台在导航栏第 5 个」·「要先选记录类型再填 id」·「那个删除弹窗点确定就行」。

「顺 / 犹豫 / 卡住」三档的定义**必须统一**，否则记录不可比：

- **顺**：没停顿，直接点对。
- **犹豫**：停了下来（>3 秒）、鼠标来回移动、先看别处、问了句「这里？」
- **卡住**：点了错的按钮、填错内容、或者超过 60 秒没动 —— 到了这一步就**记下时间点并让他跳过**，别提示他。

> 网页版的「用时」列填的是**档位**，不是精确秒数（点一下就换一档，配合上面的 3 秒 / 60 秒两条线）：  
> `3 秒内` · `3–10 秒` · `10–60 秒` · `超过 60 秒`。要精确秒数就直接写进「当时他说了什么」那一列。

## 6. 拿到记录后：怎么挑「最高优先级卡点」

### 6.1 先分级（只用这三个级别，不用「还好」「基本行」）

| 级别     | 判据（满足任一即可）                              | 严重程度    |
| ------ | --------------------------------------- | ------- |
| **P0** | 核心流程**走不完**：某步卡住 ≥2 分钟、或需要问人、或他放弃/跳过    | 直接堵死产品  |
| **P1** | 走完了，但**走错路**：点了错的按钮、填错内容、靠猜才过、绕了一大圈     | 走得通但会劝退 |
| **P2** | 走完了、也没走错，但**说了不舒服**：看不懂某句文案、不知道成功了没、字太小 | 体验扣分    |

### 6.2 再排优先级（同级别时的取舍顺序）

1. **在核心路径上**的优先于边角页面的；
2. **每个用户都会遇到**的优先于偶发的；
3. **不动接口契约、不动数据模型**的优先于要大改的（今天只允许一处小修）；
4. 花费相同的，选**改文案就能解决**的（改字最便宜、回归风险最小）。

> 今天的现实约束：只修**一处**。所以规则很简单 ——  
> **先看有没有 P0；有 P0 就修 P0。没有 P0，就在 P1 里挑「离入口最近、影响人数最多」的那一条。**

### 6.3 要写进结论的三件事

1. **事实**：第几步、他点了什么、他看到什么（原话）；
2. **判断**：为什么这算卡点（用 §6.1 的判据），不是「我觉得不好用」；
3. **改法**：改哪一处、改成什么、**明确不做什么**。

## 8. 复验最小任务（修完之后，让同一个人再走一遍）

**最小任务 = 只重走被打断的那一段，不重走全程。** 目的是「这个问题还在不在」，不是「打分」。

```text
【对象】还是同一个人、同一台设备、同一个浏览器。
【范围】只从第 __ 步走到第 __ 步（把修复点包进去，前后各多一步做上下文）。
【口令】和第一次**一模一样**，一个字都不改（改了口令，两次结果不可比）。
【只看一件事】这次他在这几步里有没有「犹豫 / 卡住」。
【判定】
  · 上次卡住、这次顺 → 修复生效（记下用时对比）
  · 两次都卡 → 没修到根上，回到 §6 重新判断
  · 上次顺、这次卡 → 先怀疑是不是改动引入了新问题（看回归项）
【记录】同样填 §4.2 那张表，只填这几行；旧记录留着做对照。
```

**降级方案**（今天请不到人时用，课程原话）：  
自己间隔 10 分钟后按同一份脚本重新操作一遍，**记录第一个找不到或看不懂的地方**。  
注意两点，否则这份降级记录是假的：

- 必须**间隔 10 分钟以上**，否则记忆还热着，等于没测；
- 用**没缓存的方式**打开（浏览器隐私窗口，或换个浏览器），否则 localStorage 里的主题等痕迹会让结果偏离真人；
- 长度上只能当 P0/P1 的**候选**，不能代替真人记录写进结论。
